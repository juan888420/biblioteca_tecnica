1. Resumen del proyecto

Vectra responde preguntas del tipo «¿qué pasa si agrego este gasto?» o «¿cuánto me cuesta este estilo de vida al año?». El usuario crea productos (gastos reutilizables con precio y frecuencia), los organiza en categorías, registra ingresos y arma escenarios que combinan productos e ingresos. Cada escenario calcula su costo mensual, a 6 y a 12 meses y qué porcentaje del ingreso consume. Los escenarios pueden incluir otros escenarios (composición).

Idea central que debes poder explicar

Un escenario no lee los productos en vivo. Al agregar un producto se guarda una instantánea (snapshot) de su nombre, precio y frecuencia en ScenarioItem. Si después cambia el precio, el escenario no se altera solo: la API informa qué escenarios se verían afectados y el usuario decide si sincroniza. Es la decisión de diseño más importante del proyecto (ADR-0005). Verificado

Evolución del producto

El historial de Git y los ADR muestran que el proyecto cambió de enfoque. Conocer esto te permite explicar por qué hay código «fósil» en el schema.

  1. Julio 2026: finance tracker clásico. Cuentas, transacciones, presupuestos, transacciones recurrentes, dashboard y reportes (commits 4657598 a a4d6a20, RFC-0012 a RFC-0016). Verificado en git log
  2. Pivote a «planes de gasto» (ADR-0004), luego corregido a escenarios financieros (ADR-0005) y a una interfaz orientada a preguntas (ADR-0006). Documentado
  3. Agosto 2026: retiro del ledger (ADR-0007, RFC-0027). Se borraron rutas, servicios y pantallas de cuentas y transacciones, pero los modelos Prisma Account, Transaction, Budget y RecurringTransaction se conservaron en el schema. Verificado
  4. Pulido visual y de errores (RFC-0028 y RFC-0029): responsive, identidad «glass», códigos de error estables y textos en español. Verificado
Documentación desfasada dentro del propio repo

.claude/CLAUDE.md todavía describe Vectra como un «personal finance tracker» y la descripción OpenAPI dice "Personal finance tracker API" (apps/api/src/plugins/swagger.ts, línea 12). El README y los ADR 0005 a 0007 reflejan el estado real. Si un entrevistador abre el repo, conviene que conozcas esta discrepancia.

Fastify 5 VerificadoFramework HTTP de la API
1. ¿Qué es?
Framework web para Node.js centrado en rendimiento y en un sistema de plugins encapsulados. Cada ruta puede declarar un schema de entrada y salida.
2. ¿Qué problema resuelve?
Enrutamiento, ciclo de vida de la petición (hooks), serialización y validación declarativa, sin escribir middleware a mano para cada caso.
3. Función en Vectra
Es la API REST completa. buildApp() registra helmet, cors, rate-limit, Prisma, JWT y Swagger, y monta 7 grupos de rutas con prefijo.
4. Integración
Con Zod mediante fastify-type-provider-zod (validación y tipos), con Prisma a través de un decorator (app.prisma) y con JWT a través de otro (app.authenticate). Los tests usan app.server con Supertest.
5. ¿Por qué encaja?
El ADR-0001 la elige como «framework HTTP / API» sin detallar el motivo. Inferido: su modelo de schemas por ruta permite generar OpenAPI y validar con la misma fuente, que es justo lo que hace el proyecto.
6. Evidencia
apps/api/src/app.ts 35-71; 7 archivos *.routes.ts.

8. Conceptos previos
Plugins y encapsulación, fastify-plugin (rompe la encapsulación para exponer decorators), hooks (onRequest, onClose), decorators, declaration merging de TypeScript (declare module "fastify").
9. Alternativas
Express (más popular, sin schemas nativos), NestJS (más estructura e inyección de dependencias), Hono (orientado a edge).

11. Errores comunes

12. En una entrevista
«La API es una app Fastify construida en una función buildApp, lo que me permite levantarla igual en producción y en tests. Cada dominio es un plugin con su prefijo; la autenticación es un decorator que las rutas usan como hook onRequest.»
Zod 4 + fastify-type-provider-zod VerificadoValidación y contrato de datos en cliente, servidor y entorno
1. ¿Qué es?
Librería para declarar schemas en TypeScript que validan datos en runtime y de los que se infiere el tipo estático (z.infer).
2. ¿Qué problema resuelve?
TypeScript desaparece en runtime: los datos externos (body HTTP, variables de entorno, respuestas del servidor) no tienen garantías. Zod las comprueba.
3. Función en Vectra
Se usa en cuatro lugares: (a) bodies, params y queries de cada ruta; (b) schemas de respuesta, que también filtran campos al serializar; (c) variables de entorno al arrancar (config/env.ts, web/src/lib/env.ts); (d) re-validación en el frontend de cada respuesta de la API (*.api.ts).
4. Integración
app.setValidatorCompiler(validatorCompiler) y setSerializerCompiler (app.ts 40-41). jsonSchemaTransform convierte los mismos schemas a OpenAPI. En el formulario, zodResolver conecta Zod con React Hook Form.
5. ¿Por qué encaja?
Documentado: «Zod valida end-to-end» (comentario en auth.api.ts 10-12). Una sola herramienta para todas las fronteras de confianza.
6. Evidencia
apps/api/src/features/*/*.schemas.ts, packages/types/src/*.ts, apps/web/src/main.tsx 12 (z.config(es()), mensajes en español).

Prisma 7 + PostgreSQL VerificadoORM, migraciones y base de datos relacional
1. ¿Qué es?
Prisma es un ORM: a partir de un archivo schema.prisma genera un cliente TypeScript tipado y migraciones SQL. PostgreSQL es la base relacional.
2. ¿Qué problema resuelve?
Escribir SQL a mano sin tipos, el mapeo entre filas y objetos, y el versionado del esquema.
3. Función en Vectra
Toda la persistencia. Los servicios reciben PrismaClient por parámetro (no lo importan), lo que facilita los tests y las transacciones.
4. Integración
Prisma 7 no usa motor en Rust: conecta con un driver adapter (PrismaPg). La URL vive en prisma.config.ts y el cliente se genera en src/generated/prisma (ignorado por git). Se expone como app.prisma.
5. ¿Por qué encaja?
Decisiones de mapeo documentadas en el ADR-0002 (Money como Decimal(12,2) + Char(3), UUID v7, índices parciales en SQL crudo).
6. Evidencia

JWT + refresh tokens rotativos + bcrypt VerificadoAutenticación de sesión
1. ¿Qué es?
JWT: token firmado que el servidor verifica sin consultar la base de datos. Refresh token: credencial de larga duración que sirve solo para obtener nuevos JWT. bcrypt: función de hash lenta y con sal, pensada para contraseñas.
2. ¿Qué problema resuelve?
Mantener sesiones sin exponer un token de larga vida a JavaScript, y guardar contraseñas de forma que una filtración de la base no las revele.
3. Función en Vectra
El access token (HS256, 15 min) viaja en Authorization: Bearer. El refresh token (256 bits aleatorios, 7 días) viaja en una cookie HttpOnly limitada a path=/auth; en la base solo se guarda su SHA-256. Cada uso lo rota, y reutilizar uno ya revocado revoca todas las sesiones del usuario.
4. Integración
@fastify/jwt firma y verifica (reply.jwtSign, request.jwtVerify); @fastify/cookie maneja la cookie; el modelo RefreshToken persiste los hashes; en el cliente, api-client.ts renueva el token de forma transparente.
5. ¿Por qué encaja?
ADR-0001 pide «JWT + Refresh Tokens» y bcrypt; las reglas de seguridad de .claude/CLAUDE.md piden cookies HttpOnly para refresh tokens. Documentado
6. Evidencia
apps/api/src/plugins/auth.ts, features/auth/auth.service.ts, features/auth/auth.routes.ts.

React 19 + Vite 6 + React Router 7 VerificadoSPA renderizada en cliente

TanStack Query 5 VerificadoEstado del servidor, caché e invalidación
1. ¿Qué es?
Librería que gestiona datos remotos: caché, reintentos, deduplicación, estados de carga y error, e invalidación.
2. ¿Qué problema resuelve?
Evita guardar datos del servidor en useState o Redux y sincronizarlos a mano.
3. Función en Vectra
Cada feature define una query key factory (*.keys.ts) y hooks (use-*.ts). Las mutaciones invalidan varias features a la vez porque los datos están relacionados (un cambio de precio afecta a la categoría y a los escenarios).
4. Integración
Llama a las funciones de *.api.ts, que a su vez usan apiRequest. Al cerrar sesión se ejecuta queryClient.clear(). Configuración global: staleTime 30 s y retry: 1.
5. ¿Por qué encaja?
ADR-0001: «data fetching, cache y sincronización». En router.tsx 17-19 se documenta que es la única fuente de estado del servidor.
6. Evidencia
apps/web/src/lib/query-client.ts, features/*/use-*.ts, features/*/*.keys.ts.

React Hook Form VerificadoFormularios con validación Zod
1. ¿Qué es?
Librería de formularios basada en inputs no controlados, con pocos re-renders.
2. ¿Qué problema resuelve?
Manejar el estado de cada campo, los errores, el envío y el reset sin escribir ese boilerplate en cada formulario.
3. Función en Vectra

5.2 Editar el precio de un producto y propagarlo a los escenarios

Es el flujo más característico del proyecto (RFC-0023.3). El producto siempre se guarda; lo que se decide después es si los escenarios que lo usan se actualizan.

  1. Inicio: el usuario edita un producto en ExpenseItemFormDialog → onSubmit (116-146) → useUpdateExpenseItem().mutateAsync.
  2. Recepción: PATCH /expense-items/:id con hook de autenticación (expense-items.routes.ts 31 y 96-115). Zod valida updateExpenseItemBodySchema.
  3. Validación de negocio: la propiedad se comprueba con findOwnedOrFail; la categoría debe existir, no estar archivada y ser de tipo EXPENSE (assertCategoryUsable, 44-61); el nombre debe ser único entre los activos sin distinguir mayúsculas (assertNameAvailable, 25-42).
  4. Persistencia: prisma.expenseItem.update y finalizeExpenseItemWrite (120-127) → reconcileExpenseItemScenarios (scenarios.service.ts 1129-1179).
  5. Lógica: para cada ScenarioItem no archivado, diffItemKinds (496-512) compara el snapshot con el producto vivo. Los cambios visuales se actualizan en lote dentro de una $transaction; los financieros se acumulan. Después collectAncestorScenarioIds (904-927) sube por la composición para encontrar también los escenarios padre.
  6. Respuesta: { data, affectedScenarios, changes }; cada cambio lleva from/to, con from: null si los snapshots tenían valores distintos (collapseFrom, 965-972).
  7. Frontend: useScenarioImpact.report abre el diálogo (use-scenario-impact.ts 37-41). «Aplicar ahora» → syncExpenseItemScenarios (1186-1234), que vuelve a detectar los cambios en el servidor en lugar de confiar en la lista del cliente.
  8. Errores: DUPLICATE_NAME aparece bajo el campo de nombre; el resto llega como toast con texto de getErrorMessage(error, "expenseItem").

5.4 Cálculo del resumen de un escenario

GET /scenarios/:id/summary → getScenarioSummary (1415-1487):

  1. collectReachableScenarioIds (875-896): el escenario y todos sus descendientes por composición.
  2. Lee los ScenarioItem de todos esos escenarios (los gastos sí se heredan) y los ScenarioIncome solo del escenario raíz (los ingresos no se heredan, RFC-0023.1 §9).
  3. Suma el equivalente mensual con toMonthlyEquivalent (anual ÷ 12, semanal × 52 ÷ 12); los ONE_TIME se suman aparte.
  4. Cobertura: consumedPercentage = monthly / totalIncomeMonthly × 100, o null si no hay ingresos.
  5. pendingChanges sale de detectScenarioChanges (solo los financieros), y hasUpdates = pendingChanges.length > 0. Nada de esto se guarda en la base.
Punto de rendimiento verificable

listScenarios (55-89) calcula monthly para cada fila con getScenarioMonthlyTotal, que a su vez hace un BFS y otra consulta. Una página de 20 escenarios genera decenas de consultas. 5.5 Manejo de errores de punta a punta

  1. El servicio lanza un HttpError tipado: badRequest, unauthorized, notFound o conflict (apps/api/src/lib/http-errors.ts 10-38).
  2. El manejador global (plugins/error-handler.ts 28-80) distingue cuatro casos: errores de validación Zod (400 con issues), fallos de serialización de la respuesta (500), errores HttpError propios (se reenvía su mensaje) y cualquier otro error (se registra en el log y se responde con un mensaje fijo, en todos los entornos).

12. Hallazgos y limitaciones técnicas observables

Son observaciones del código, no incidentes. Sirven para preparar respuestas del tipo «¿qué mejorarías?».

  1. Dinero como Number: Decimal(12,2) se convierte con Number(...) para sumar y prorratear (getScenarioSummary, toPublic). Con valores grandes o divisiones (÷ 12, × 52 ÷ 12) aparecen errores de coma flotante. Alternativas: Prisma.Decimal, decimal.js o trabajar en centavos enteros.
  2. Consultas N+1 en grafos: reaches, collectReachableScenarioIds y collectAncestorScenarioIds hacen una consulta por nodo; listScenarios repite el proceso por fila. Alternativa: una CTE recursiva (WITH RECURSIVE) con $queryRaw.
  3. Condiciones de carrera check-then-act: la unicidad de nombres, la detección de ciclos y la detección de reutilización del refresh token leen y luego escriben fuera de una transacción serializable.
  4. Sin CI ni Docker, aunque estén en el ADR-0001 y en el diagrama de stack del README.
  5. Sin tests de auth y solo un test de frontend.
  6. Documentación desfasada: .claude/CLAUDE.md y la descripción de Swagger hablan de «finance tracker»; el ADR-0003 enlaza lib/recurrence.ts, que se eliminó en RFC-0027; los RFC citados no están en el repo.
  7. Código sin consumidores: DataTable, la prop badge de StatCard, vectra-logo.png, los endpoints /scenarios/:id/changes y la dependencia recharts (los cuatro primeros los reconoce docs/resumen.md).
  8. Sin lazy loading de rutas.
  9. Swagger UI expuesta sin condicionar por entorno.

13.2 Preguntas y respuestas

Junior ¿Por qué guardas el access token en memoria y no en localStorage?
Qué evalúa
Conocimiento básico de XSS y del almacenamiento en el navegador.
Conceptos
XSS, cookies HttpOnly, alcance de localStorage.
Respuesta sugerida
Cualquier script inyectado puede leer localStorage. Mantengo el access token en una variable de módulo (api-client.ts 21-24), que se pierde al recargar. Para no perder la sesión, el refresh token vive en una cookie HttpOnly que JavaScript no puede leer, y al cargar la app se restaura la sesión con /auth/refresh.

apps/web/src/lib/api-client.ts 21-32; AuthProvider.tsx 20-36.
Seguimiento
¿Y si hay XSS de todos modos? (El atacante puede hacer peticiones mientras la página esté abierta, pero no puede robar el refresh token para usarlo después.)
Evita
Decir que las cookies HttpOnly «eliminan» el riesgo de XSS.

Intermedio Explica la rotación de refresh tokens y la detección de reutilización.
Qué evalúa
Diseño de autenticación más allá de «uso JWT».

13.4 Resolución de problemas

Escenarios hipotéticos para practicar: ninguno corresponde a un incidente documentado, salvo donde se indica.

  1. «Los usuarios se desconectan al abrir dos pestañas.» Hipótesis: dos refresh simultáneos desde pestañas distintas disparan la detección de reutilización. Diagnóstico: logs de «Refresh token reuse detected». Opciones: periodo de gracia para el token anterior, coordinar pestañas con BroadcastChannel o lock en la base.
  2. «La lista de escenarios tarda varios segundos.» Hipótesis: N+1 en getScenarioMonthlyTotal. Medición: logs de consultas de Prisma. Solución: una CTE recursiva por lote.
  3. «Un total mensual muestra 33,333333.» Prorrateo con Number. Solución: redondeo controlado y aritmética decimal.
  4. «Se creó un ciclo de composición.» Carrera entre dos peticiones. Solución: transacción serializable o restricción mediante trigger.
  5. Problema documentado en el historial: StrictMode ejecutaba dos veces el refresh de arranque y uno de los dos fallaba al reutilizar la cookie. Solución aplicada: useRef como guardia (AuthProvider.tsx 14-25). Documentado en el código
  6. Problema documentado: Windows bloqueaba el binario de migraciones de Prisma. Solución aplicada: el script db:apply. Documentado
